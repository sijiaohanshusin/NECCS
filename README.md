## 总述

NECCS 是一个基于 **STM32H743** 的嵌入式声学相机工程，目标是在资源受限的 MCU 平台上完成 **16 路麦克风阵列采集、实时声源定位、图形化显示、在线调参与运行诊断**。工程已经具备较完整的“采集 → 算法 → 显示 → 调试”链路，适合作为以下工作的基础：

- 声源定位算法验证与性能优化。
- MCU 端声学相机产品原型开发。
- 麦克风阵列、LCD、SDRAM、DMA、FreeRTOS 协同设计参考。
- 后续任务规划，例如显示效果增强、串口控制扩展、摄像头融合、系统稳定性改进等。

本 README 的目的不是只告诉读者“如何编译”，而是从 **项目定位、系统结构、目录职责、数据流、运行方式、约束风险、扩展方向** 多层次梳理整个工程，帮助后来者快速建立整体认知，并据此拆解未来任务。

# 第一层：项目全景

## 1.1 项目要解决什么问题

该工程面向“实时声源方向感知”场景：

- 使用 16 路 PDM 麦克风采集环境声音。
- 通过双芯片音频前端将 PDM 转为 MCU 可处理的 TDM/SAI 数据流。
- 在 STM32H743 上执行频域处理与 SRP-PHAT 声源定位。
- 将定位结果与能量分布可视化输出到 800×480 LCD。
- 通过串口提供在线调参、状态查询与运行诊断能力。

换句话说，这个工程既是一个 **实时信号处理系统**，也是一个 **硬件驱动 + RTOS 调度 + 图形显示 + 工具链工程化** 的综合样板。

## 1.2 当前工程的核心特征

### 硬件侧

- 主控：`STM32H743IIT6`，主频 480MHz。
- 音频前端：`2 × PCMD3180`，用于 16 路麦克风采集。
- 显示链路：RGB LCD + LTDC，分辨率 800×480。
- 外部存储：32MB SDRAM，用于帧缓冲及大块数据承载。
- 调试/控制接口：USART、I2C、SAI、DMA。
- 工程内还存在摄像头相关代码与资料，说明项目有向“声学 + 图像”融合扩展的潜力。

### 软件侧

- 操作系统：FreeRTOS。
- 音频处理流程：采集、解交织、预处理、FFT、GCC/SRP-PHAT、定位输出。
- UI 处理流程：位置读取、画面渲染、文字叠加、显示输出。
- 运行期能力：性能统计、串口 CLI、运行模式切换、显示参数动态配置。
- 工程形态：以 STM32CubeMX 生成框架为底座，叠加自定义应用层、算法层和 BSP/硬件层。

## 1.3 这个 README 适合谁看

- **新接手项目的开发者**：先看总体结构、目录职责和启动流程。
- **做算法优化的人**：重点看算法层、数据流、性能预算、运行参数。
- **做板级/驱动联调的人**：重点看硬件层、初始化顺序、内存与 DMA 约束。
- **做产品规划或任务拆解的人**：重点看“现状边界”“风险点”“建议路线图”章节。

# 第二层：系统分层理解

## 2.1 硬件与外设层

这一层负责“让系统真正拿到数据并把结果显示出来”。

### 输入链路

- 16 路麦克风阵列产生 PDM 数据。
- 两片 `PCMD3180` 负责音频前端采集与格式桥接。
- MCU 侧通过 `SAI + DMA` 接收音频数据。
- `soft_i2c` 提供对音频前端器件的配置能力。

### 输出链路

- LCD、LTDC、DMA2D 相关模块负责图像输出。
- SDRAM 提供显示帧缓冲和大体量图像数据存放空间。
- 串口承担日志输出、CLI 命令输入、状态查询等辅助交互。

### 为什么这一层重要

如果输入链路不稳定，算法再好也没有意义；如果显示链路或内存布局不合理，实时性就会迅速恶化。因此本项目在主程序中显式包含：

- SDRAM 初始化与上电自检。
- SAI/DMA 启动与时钟稳定等待。
- 音频前端初始化任务。
- 显示后端与内存布局优化说明。

## 2.2 系统服务与调度层

这一层的关键是 **FreeRTOS 任务编排** 与 **启动顺序控制**。

### 主要任务角色

- `PCMD3180InitTask`：一次性高优先级初始化任务。
- `Audio_Pipeline_Task`：高实时性音频处理任务。
- `UI_Display_Task`：周期性 UI 渲染任务。
- `StartDefaultTask`：低优先级保留任务。

### 设计意图

- 初始化任务与工作任务分离，避免在 `main()` 中堆叠复杂的阻塞初始化逻辑。
- 音频任务与 UI 任务通过队列解耦，只保留“最新一帧/最新一组结果”，减少延迟累积。
- 串口 CLI 由 UI 任务轮询，降低额外线程数量与并发复杂度。

### 对未来规划的意义

这说明后续新增功能时，最好优先考虑：

- 是否可以挂载到现有任务，而不是盲目增加新任务。
- 是否应该通过深度为 1 的覆盖队列维持“最新状态”语义。
- 是否需要像初始化任务一样设计“一次性任务 + 自删除”的模式。

## 2.3 算法处理层

这一层负责把音频样本转换为“可解释的位置结果”。

### 主要内容

- 通道解交织。
- 数据格式转换与预处理。
- FFT 频域变换。
- GCC/PHAT 相关处理。
- SRP-PHAT 粗搜 + 精搜。
- 置信度/质量评估。

### 设计特点

- 偏向 MCU 可落地实现，而非仅做理论最优。
- 通过查找表与分阶段搜索缩短计算路径。
- 在精度、稳定性、时间预算之间做平衡。

## 2.4 应用与交互层

这一层面向“人如何理解系统当前状态”。

### 主要能力

- 实时渲染定位结果和热力图。
- 支持不同显示质量/速度模式。
- 提供在线参数调节命令。
- 输出性能统计与 DMA2D 状态。
- 形成现场可调、可观测、可诊断的使用体验。

这意味着本工程不只是一个算法 Demo，而是已经开始具备 **可维护应用** 的形态。

# 第四层：运行流程与数据流

## 4.1 启动流程

系统启动大致可分为以下阶段：

1. 配置 MPU。
2. 执行 HAL 初始化。
3. 应用工程自定义 MPU 布局并开启 Cache。
4. 配置系统时钟到 480MHz。
5. 初始化 SDRAM。
6. 初始化 GPIO、DMA、USART、SAI 等外设。
7. 初始化显示模块。
8. 执行上电自检（当前重点是 SDRAM 测试）。
9. 创建 FreeRTOS 基础任务。
10. 在 `PCMD3180InitTask` 中完成软 I2C、数据流、应用任务、音频前端、摄像头等初始化。
11. 进入持续运行阶段，由音频任务与 UI 任务长期工作。

## 4.2 实时数据流

```text
麦克风阵列
  -> PCMD3180 × 2
  -> SAI + DMA 采样
  -> 音频帧事件投递
  -> Audio_Pipeline_Task
  -> 解交织/预处理/FFT/SRP-PHAT
  -> 位置结果队列
  -> UI_Display_Task
  -> 热力图/文字叠加/LCD 输出
  -> 串口状态输出与在线调参
```

## 4.3 关键并发关系

### 音频任务

- 对实时性最敏感。
- 应优先保证处理时间不要持续超过音频帧周期。
- 若未来加功能，应避免在该任务中做重 IO、重日志、重内存拷贝。

### UI 任务

- 负责显示与 CLI 轮询。
- 可以承载适量低实时性逻辑，但仍需避免因绘制或串口阻塞影响整体流畅性。

### 初始化任务

- 只运行一次。
- 适合放需要 RTOS 资源支持、但又不应长期占用 CPU 的启动工作。

# 第五层：算法与性能理解

## 5.1 当前算法主线

项目采用 SRP-PHAT 思路完成声源定位，整体流程可概括为：

1. 采集多通道音频。
2. 将原始数据变换到频域。
3. 计算通道对之间的相位相关信息。
4. 在候选方向网格上累计功率。
5. 通过粗搜快速找到大致方向。
6. 对候选峰值区域进一步精搜。
7. 输出角度、能量与质量指标。

## 5.2 算法实现上的工程化取舍

### 为了速度做的取舍

- 使用预计算查找表。
- 使用粗搜 + 精搜而非全局高密度扫描。
- 在频率 bin 范围上做限制。
- 通过固定结构和固定缓冲减少动态分配。

### 为了稳定性做的取舍

- 使用 PHAT 白化增强直达声特征。
- 提供质量/对比度阈值判断。
- 支持在线调节噪声、平滑、增益等显示相关参数。

### 为了可维护性做的取舍

- 算法、应用、硬件分目录组织。
- 配置集中在头文件和运行时配置模块中。
- 通过工具脚本生成或校验相关数据，而不是全靠手工维护。

## 5.3 性能关注点

从项目现有说明来看，性能瓶颈主要集中在：

- FFT 与多通道频域处理。
- GCC/PHAT 或相关互相关计算。
- SRP 网格搜索。
- LCD 刷新和内存搬运。
- SDRAM / AXI SRAM / DTCM / D2 SRAM 间的数据放置与带宽冲突。

因此未来做优化时，建议始终同时看两个维度：

- **CPU 时间预算**：是否影响音频实时性。
- **内存/总线压力**：是否导致显示卡顿、DMA2D 回退、链路不稳定。

# 第六层：运行、调试与日常开发方式

## 6.1 构建方式

当前主工程使用 **Keil MDK-ARM**：

1. 打开 `START/MDK-ARM/START.uvprojx`。
2. 选择目标配置。
3. 编译与下载。
4. 结合 ST-Link/J-Link 进行调试。

## 6.2 在线调参与状态查询

项目已经内置串口 CLI，适合现场联调和参数试验。

### 已记录的命令类型

- 帮助：`help`、`cfg help`
- 状态：`cfg status`
- 模式切换：`cfg mode fast|balanced|clean`
- 对比度/伽马/噪声/自适应/平滑/细化：`cfg contrast`、`cfg gamma`、`cfg noise`、`cfg adapt`、`cfg smooth`、`cfg fine`
- 刷新相关：`cfg bilinear`、`cfg textdiv`、`cfg blit`

### 对任务规划的价值

这意味着很多“显示效果优化”与“现场参数试验”并不需要先改代码再烧录，可以先通过 CLI 确认方向，再决定是否固化为默认配置。

## 6.3 现场排障建议

### 启动阶段异常

优先检查：

- SDRAM 自检是否通过。
- PCMD3180 初始化是否完成。
- SAI/DMA 是否已启动。
- Boot 诊断阶段停在什么位置。

### 显示异常

优先检查：

- 帧缓冲是否正确落在 SDRAM。
- DMA2D 是否出现 timeout 或 fallback 增长。
- 显示内存节省等级是否需要调整。

### 定位效果异常

优先检查：

- 采集通道是否完整。
- 麦克风阵列接线和相位一致性。
- SRP 参数范围是否合适。
- 噪声门限与显示参数是否掩盖真实现象。

# 第七层：工程的边界、现状与风险

## 7.1 这个工程已经做到了什么

- 已具备完整的嵌入式声源定位主链路。
- 已具备显示和运行诊断能力。
- 已开始关注链接布局、内存压力、DMA2D 回退等工程问题。
- 已具备一定的在线调参与现场使用基础。
- 已出现摄像头相关代码，说明系统具备功能扩展空间。

## 7.2 这个工程还不等于什么

- 还不能简单视为“最终量产方案”。
- 还需要更多硬件一致性、场景鲁棒性、异常恢复、测试覆盖方面的完善。
- 摄像头链路虽然已有代码与资料，但是否形成完整融合产品能力，还需要进一步验证。

## 7.3 当前值得长期关注的风险

### 风险一：实时性边界紧张

音频处理和显示共享 MCU、总线与存储资源，新增功能很容易突破时间预算。

### 风险二：内存布局持续演化

一旦新增大数组、帧缓存或查表，链接布局可能再次溢出，或导致 DMA/Cache 交互问题。

### 风险三：模块能力增长快于文档更新

项目已有较多运行期能力和调试约定，如果 README、运行说明、参数说明不持续更新，新成员理解成本会迅速增加。

### 风险四：多功能融合复杂度上升

如果未来同时推进音频、显示、摄像头、串口协议，任务优先级与带宽分配会更复杂，必须强化架构约束。

### 主线 C：可维护性与可观测性增强

- 完善 README、运行手册、串口命令说明。

- 建立统一日志级别与诊断字段定义。
- 补充模块边界说明，降低隐式耦合。

### 主线 D：功能扩展

适合拆解的任务包括：

- 完善摄像头模块接入与图像显示链路。
- 设计音频 + 图像融合的人机界面。
- 引入结果录制、回放或导出机制。
- 扩展串口协议或上位机控制能力。
- 探索多声源场景或更复杂定位模式。

## 8.2 建议的任务优先级

如果资源有限，推荐优先级为：

1. **稳定性与可观测性**：先确保系统可测、可诊断、可复现。
2. **实时性与内存安全**：避免新功能破坏主链路。
3. **算法效果提升**：在稳定基线之上做性能/精度优化。
4. **功能扩展**：最后再叠加摄像头、协议、复杂交互。

## 8.3 给后续开发者的任务拆解模板

建议每个新任务都回答以下问题：

- 目标属于哪个层：硬件层、调度层、算法层、应用层、文档层？
- 是否影响音频实时路径？
- 是否新增大块内存或长期缓冲？
- 是否需要新增 CLI 参数或状态输出？
- 是否需要同步更新 `README.md`、运行说明或内存说明？
- 是否能通过脚本/离线工具先验证，再上板联调？

这样可以避免“代码改了，但系统认知和文档没有跟上”的问题。

# 第十层：维护本 README 的建议

为了让这个文档持续帮助后续任务规划，建议以后遵守下面原则：

- **新增功能时，同步更新“项目全景”和“目录职责”。**
- **新增运行参数时，同步更新“运行、调试与日常开发方式”。**
- **新增大块内存/链路策略时，同步更新“边界、现状与风险”。**
- **新增里程碑任务时，同步更新“未来任务规划建议”。**

如果文档只记录“怎么编译”，它对长期维护的价值会非常有限；而如果文档持续记录“系统为什么这么设计、下一步应该怎么规划”，它就会成为整个工程最重要的认知入口之一。
